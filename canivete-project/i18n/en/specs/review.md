# Task `review` — security and quality review (final gate)

You are the last step of the swarm. The Pocketknife runs in each participant's browser and loads code written by agents: a server that lets files out, or a tool that touches the DOM, would be the worst possible example. You do not fix code: you give a verdict with concrete problems.

## What you read, and only this

1. `.workshop/review-summary.md`, generated by `tools/review-digest.mjs`. It contains three things:
   - the task table;
   - the static checks: CSP in the server, whether it binds only to `127.0.0.1`, how many tools have a `tool.js`, and the dangerous patterns found in `tools/*/tool.js`, `public/`, `pages/`, `templates/` and `lib/`;
   - the list "Files to review closely".
2. The files on that list, and no others. If the digest points to a dangerous pattern in a file that is not on the list, read that one too.

Do not explore the rest of the project. The budget is tight.

## Checklist

### `server.js`
- Binds only to `127.0.0.1`.
- Every response carries the CSP without `'unsafe-inline'` or `'unsafe-eval'`, including error, JSON and SSE responses. The expected CSP has `default-src 'self'`, `script-src 'self'`, `style-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'` and `require-trusted-types-for 'script'`.
- It also sends `X-Content-Type-Options: nosniff`, `Referrer-Policy` and `Cross-Origin-Opener-Policy`.
- **Path traversal:**
  - the path is decoded before it is validated;
  - it refuses segments that start with `.` (catches `..`, `.workshop`, `.claude`, `.git`), `\`, NUL and `:`;
  - it resolves inside the allowed folder and confirms with `realpath`, because of symbolic links;
  - it serves only `public/`, `templates/*.js`, `lib/*.js`, `pages/*.js`, `replays/<name>/*.json(l)` and, from `tools/`, **only** `tools/<id>/tool.js` and `tools/<id>/tool.test.js`, and only known extensions;
  - `server.js`, `package.json`, `plan.json`, `specs/` (`specs/my-tool.json` too), `.workshop/` and the rest of `tools/` (`gen.mjs`, `workshop/`…) are never served.
- `/api/tools` sends only the fields the shell uses (it never copies `specs/my-tool.json` as it is) and `/api/replay/<name>` validates the name with a regular expression before touching the disk.
- No `eval`, no `child_process`, no reading of `.env`. An error does not send the stack trace to the browser.

### The shell: `public/app.js`, `public/tool-view.js`, `public/finder.js`, `public/testrun.js`, `public/dom.js` and `public/status.js`
- **Data in the DOM:** only through `textContent`, `createTextNode` or `el()` from `public/dom.js`. Never `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `srcdoc` or `on…=`. A tool's result and what the person types always show up as text.
- The ids that come from the hash (`#/tool/<id>`) and from `/api/tools` are validated before they go into an `import()` or a URL. The `href`s are internal only.
- `sessionStorage` is inside `try/catch` and stores nothing sensitive. The shell's randomness (`crypto.getRandomValues`) is only for the seed of the `generate` template.
- No `eval`, `Function` or `setTimeout` with a string.

### `pages/catalog.js`
- A pure module: no `document`, `window`, `fetch`, storage or `import()`; imports only from `../lib/` and `../templates/`.
- It does not change the lists or the objects it receives.
- It follows `specs/index-page.md`: the search ignores case and accents and looks in the id, the title, the concept and the category name; the groups come in the order of the categories.

### `templates/common.js` and `templates/generate.js`
- `run()` returns `{ error }` only for a `ToolError`; any other exception is not hidden.
- The randomness of `generate` comes only from the seed (no `Math.random`).

### The tools (`tools/<id>/tool.js`)
Review only the ones the digest points to (a dangerous pattern, or a task that failed for good).
- They only compute: no DOM, no network, no storage, no `eval`, no `Function` and no `Math.random`; imports only from `../../templates/` and `../../lib/`.
- They use the template of the spec and throw `ToolError` with the spec's message for the inputs they do not accept.

### Secrets, in every file you read
Look for keys and tokens in the code: `sk-ant-`, `ghp_`, `AKIA`, `-----BEGIN` and `password =` with a literal value.

## Severity

| `severity` | When |
|---|---|
| `high` | Exploitable: XSS, path traversal, a file outside the list being served, CSP missing or with `unsafe-*`, server open beyond 127.0.0.1, a secret in the code. |
| `medium` | A missing defence with no direct exploit; a tool that uses `Math.random` or touches the DOM; a task that failed for good (one issue per task, up to 3). |
| `low` | Quality: text that is not plain English, dead code, confusing names. |

## Verdict

- `rejected`: there is at least one `high` issue.
- `approved_with_reservations`: there are issues, but none is `high`.
- `approved`: there are no issues.

## Result: `.workshop/verdict.json`

Valid JSON, no comments, with exactly these fields:

```json
{
  "verdict": "approved_with_reservations",
  "summary": "The server and the shell pass the critical points: strict CSP, refused paths and DOM only through textContent. One reservation remains: the tool nm-03 failed for good and shows as to build.",
  "issues": [
    {
      "severity": "medium",
      "file": "tools/nm-03/tool.js",
      "description": "The task failed for good: run() rounds 1.005 with toFixed(2) and returns 1 instead of 1.01.",
      "fix": "Complete the rule in tools/nm-03/spec.md and run /demo-swarm --retry nm-03."
    }
  ]
}
```

- **`summary`:** two sentences.
- **`issues`:** at most 8, from the most to the least severe. Each `description` has up to 200 characters and says where the problem is (function or line). Each `fix` says what to change and where. With no issues, `issues` is `[]`.
- Keep the keys and the values of `verdict` and `severity` exactly as they are: the orchestrator reads them.
- Text in English.
- Do not change any other file.

At the end, answer with ONE single line: `OK review: <verdict>`.
